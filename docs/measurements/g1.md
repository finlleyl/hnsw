# G1: split writer

`Add` plans and prepares slice growth without the read/write lock, then publishes under
`mu.Lock`. This gate compares that with holding `mu` for the whole insert after private
normalization. The API and graph construction are the same in both modes.

**Setup.** darwin/arm64, Apple M4 Pro, go1.26.2. Clustered synthetic data, M=16,
EfConstruction 200, seed 7, k=10 and ef=100. The base indexes have n=100k at d=128 and
n=50k at d=768. Eight readers run held-out queries while one writer adds 100 vectors per
second. Each mode runs for three seconds (300 inserts), with index construction excluded.
The command is:

```sh
go test -run '^$' -bench '^BenchmarkReaders100Adds$' -benchtime=3x -count=1
```

The p99 is over all Search calls in the three measured seconds. Maximum publish is the
longest `g.publish` call, including its map inserts but excluding lock and unlock overhead.

| d | n | Split Search p99 | Whole-Insert Search p99 | Split max publish |
|---|---:|---:|---:|---:|
| 128 | 100000 | 200.8 µs | 268.4 µs | 3.3 µs |
| 768 | 50000 | 522.5 µs | 1076.3 µs | 8.0 µs |

## Result

Pass. Split Search p99 is below the whole-Insert rerun on the same machine at both
sizes, so the split writer stays. The whole-Insert figures also rerun the baselines that
were 306 µs and 1190 µs in the design; the gate is the same-run comparison, not those old
absolute numbers. Only this darwin/arm64 setup was measured.
