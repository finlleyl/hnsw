# G5: real embeddings

**Setup.** darwin/arm64, Apple M4 Pro, 24 GiB RAM, go1.26.2, GOMEMLIMIT=18GiB. Dataset:
[Qdrant/dbpedia-entities-openai3-text-embedding-3-large-3072-1M](https://huggingface.co/datasets/Qdrant/dbpedia-entities-openai3-text-embedding-3-large-3072-1M),
commit b2f301648eda4c5dbe659235589c86ffec702581. The first 1000 rows are held-out queries;
the other 999000 are inserted in dataset order with integer keys. The float64 embeddings are
converted to float32, truncated to d=768 or 1536 where applicable, and normalized with the
index's normalization algorithm. All configurations have 999000 nodes: no vectors merged.

Each configuration uses EfConstruction=200 and seed 7. Exact truth is a brute-force scan over
the base vectors. Recall@10 is tie-aware with 2e-6 rounding slack, as in `index_test.go`.
Build time includes reading normalized float32 vectors and sequential Add calls, but excludes
truth and SaveFile. Each build runs in a fresh process; raw vectors are not retained together
with the index. The measurement harness and pinned dependencies are in
`docs/measurements/gates`, not the root module.

| 1536 | 16 | 1807.5 | .9669 | 320 | .9911 | 2.549 |
| 3072 | 16 | 2916.5 | .9714 | 320 | .9913 | 3.713 |

All M=16 configurations crossed .99 only at ef=320:

| d | ef=100 | ef=160 | ef=240 | ef=320 |
|---:|---:|---:|---:|---:|
| 768 | .9755 | .9842 | .9894 | .9911 |
| 1536 | .9669 | .9836 | .9884 | .9911 |
| 3072 | .9714 | .9808 | .9878 | .9913 |

For d=768, M=8, recall was .9489 at ef=160, .9634 at 240, .9707 at 320, .9767 at 480,
.9799 at 640, .9858 at 960, .9898 at 1280 and .9926 at 1920. M=32 passed at ef=160 after
.9897 at ef=100.

**Default consequence applied.** Every M=16 configuration missed .99 at the old default
ef=100 and passed at 320. `Options.Ef` now defaults to 320; `TestDefaults` pins the change.
This is a recall decision, not a claim that 320 is optimal for other datasets.

## Rebuild versus bridge

For compaction, keys where `key % 10 < 3` were deleted (30% uniform deletion), leaving
699300 live keys on 999000 nodes. Exact truth was recomputed over only the live keys. Recall
below is at ef=100. Rebuild is the production `Compact` path. Bridge is a temporary test-only
prototype: for each live node it gathers live one- and two-hop neighbours, removes dead links,
and applies Algorithm 4. It does not reclaim tombstone storage, so the comparison is repair
cost and recall, not a production-ready replacement for Compact.

| Method | Seconds | Nodes after | Recall@10 | ms/query |
|---|---:|---:|---:|---:|
| Rebuild | 844.9 | 699300 | .9731 | .756 |
| Bridge prototype | 259.8 | 999000 | .9726 | .671 |

**Bridge consequence scheduled.** Bridge repair was 3.25x faster than rebuild, and its recall
was only .0005 lower, meeting both parts of the gate. Production bridge compaction is
therefore scheduled post-v1. It still needs tombstone storage reclamation and the production
concurrency, persistence and invariant work; this measurement does not change the current
Compact implementation.

## Reproduce

From `docs/measurements/gates`:

```sh
go run ./g5 -mode=download
go run ./g5 -mode=prepare
for d in 768 1536 3072; do go run ./g5 -mode=truth -d="$d"; done
for config in '768 8' '768 16' '768 32' '1536 16' '3072 16'; do
  set -- $config
  GOMEMLIMIT=18GiB go run ./g5 -mode=run -d="$1" -m="$2"
done
GOMEMLIMIT=18GiB go run ./g5 -mode=compact -d=768 -m=16
```

Downloaded Parquet, normalized vectors, saved indexes and JSONL output stay in ignored `data/`.
The bridge instrumentation was not committed. This was one dataset, one query split and one
machine; other real datasets and linux/amd64 build cost remain unmeasured.
